How a TLS client decides to trust a server

One question: when a client opens https://api.example.com, what does it check before it sends a byte of HTTP, and where can that fail? Scroll. The graphic on the left tracks the text on the right.

What is what
leaf
the server's own certificate, names the hostname
intermediate
a CA certificate that signed the leaf, sent by the server
root
the self-signed top of the chain, never sent, must be in the store
trust store
the roots the client ships with (OS, browser, or a tool's own bundle)
SNI
the hostname the client asks for in ClientHello

Start. The client has one asset: a list of root certificates it was shipped with. Everything below follows from that list.

ClientHello. The client says which hostname it wants. The server uses that to pick a certificate. Nothing is trusted yet.

Certificate chain arrives. Leaf plus intermediate. The root is not sent. If it were, the client would ignore it: a server cannot vouch for itself.

Leaf check. Signature verified with the intermediate's public key. Validity dates checked. The requested hostname must be in the SAN list.

Intermediate check. Signature verified with the root's public key. The client has that key only if it can find the root. Where does it look?

Store lookup. The intermediate names its issuer. The client searches its store for a root with that subject. A miss here is unable to get local issuer certificate, the error you see behind a corporate proxy from pip or Java.

Anchored. Every link is verified and the top link is in the client's own store. Only now does key exchange proceed and the connection becomes encrypted to the right party.
